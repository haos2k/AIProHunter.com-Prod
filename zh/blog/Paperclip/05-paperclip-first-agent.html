Paperclip 第一個 agent 怎麼設？角色、Codex 連線與首次執行

2026 年 11 月 28 日·10 min read

「雇 AI 員工」聽起來很大，其實你第一步只需要決定三件事：它做什麼、用哪個模型執行、一次能花多少。本站的虛構小店案例從一名「內容企劃」開始，之後才加入資料查核、貼文編輯與內容校對。

手機閱讀時可點開操作截圖，查看原尺寸。

這是 2026 年 11 月 25 日的本機畫面。CEO、Researcher、General、QA 是 Paperclip 的角色；「內容企劃」等中文名稱方便人辨認。第一名 agent 雖叫內容企劃，在組織圖中仍是 CEO，因為它是根節點，其他 agent 向它回報。官方核心概念把 Agent 定義為有職責、主管、adapter 與預算的執行單位。

Agent 和模型是兩層設定

Paperclip 不自行寫文案。它透過 adapter 啟動你選的模型或本機工具。這次我選 codex_local，因為本機已安裝並登入 Codex CLI。官方 Codex adapter 文件列出它如何接任務、建立執行環境與檢查登入；換成 Claude Code 時，登入方式和畫面會不同。

建立 agent 時，先寫一段範圍清楚的職責，比取一個華麗職稱更重要。內容企劃負責拆任務與交付；資料查核只能把客戶給的資訊分為「已提供／待確認」；貼文編輯要用查核過的資訊寫草稿；內容校對按字數、禁語與待確認欄位驗收。若一名 agent 同時研究、寫作、批稿，又沒有工單界線，出了錯很難知道該修哪一步。

上圖是 agent 的詳細頁；建立後還應打開 Harness／Runtime，執行環境測試，再交第一張工單。本站的正式 agent 是從本機 API 建立，網頁畫面則是建立後的真實結果。一般讀者可直接在網頁的 New Agent 走設定流程。

第一張測試工單該交什麼？

agent 建好後，先交一張十分鐘內能人工看完的測試任務，例如「根據以下四項店家資料，列出可用事實與待確認問題，不寫貼文、不對外發布」。這比直接要求完整內容包容易驗收：輸入只有四項，輸出應該是一張清單；如果它編了價格或獎項，你能立刻指出問題。這是給讀者的試跑建議，本站實測則從內容企劃的三則貼文工單開始。

檢查結果時同時打開工單頁與 Runs。工單頁告訴你 agent 留下什麼內容、任務現在是什麼狀態；Runs 告訴你執行是否真的啟動、何時結束、失敗原因是什麼。若只有執行成功卻沒有對應工單結果，先不要把它算成交付。本站的公司層級 heartbeat 就是這種情況。

第一次執行為什麼失敗？

我一開始替 Codex agent 指定 gpt-6.1-sol，本機 ChatGPT 登入回報 model_not_found：這個帳號當時不能透過 Codex 使用該模型。當時 Paperclip 的 Runs 頁留下失敗紀錄，工單頁也出現錯誤留言。我移除指定模型，讓 Codex CLI 使用它自己的預設模型；後續成功執行的用量紀錄顯示為 gpt-6-sol。

遇到同類錯誤時，先看三層：Codex CLI 在本機是否登入、Paperclip 選的 adapter 能否找到它、指定模型是否對你的帳號開放。codex login status 可檢查本機登入狀態，但登入成功不保證任何模型名稱都可用。模型清單和可用性會變，寫教學時以當天介面與官方文件為準。

這次還有一個意外：第一次成功的手動 heartbeat 是「公司層級」，沒有帶工單。agent 回報它找不到任務，不能把那次成功狀態算成貼文已完成。真正產出三則草稿的是後來連到工單的重試執行。我們依執行紀錄和工單留言核對，而非看到綠色成功就當作交付。

看到「成功」，還要確認什麼？

第一次工單重試後，三則草稿確實出現在留言中，但狀態仍停在 in_progress。如果你只看文字，會以為工作結束；只看狀態，又可能以為 agent 完全沒做。比較可靠的檢查順序是：先看 Runs 的執行結果，再讀工單留言與交付物，最後核對工單狀態及是否需要人工移到審核。狀態和內容不一致時，將原因記在工單裡，避免同事或下一個 agent 重做。

這次 agent 說它無法從執行環境連回本機 Paperclip API，系統仍保留了完成摘要。這表示任務產出和狀態同步是兩個獨立環節；遇到類似狀況時，不要因為有摘要就自動批准文案，也不要因狀態沒變就忽略已產生的內容。

四名 agent 為什麼不能共用同一個職責？

「內容企劃」把委託拆成任務，「資料查核」界定可用事實，「貼文編輯」負責成稿，「內容校對」按規則退回或通過。四個名字看似只是分工標籤，實際價值在於交付物不同：查核交的是資料表，編輯交的是草稿，校對交的是逐項判定。若你要求校對 agent 順手改寫正文，下一次就難以分辨它是在驗收還是在替編輯做決策。

不過也不必一開始照抄四人配置。先問自己的工作是否有真正的交接點：是否有人需要在寫作前查事實？是否有人要在交付前獨立驗收？如果都沒有，單一 agent 加上一張清楚工單可能更適合。這次用四名 agent，是為了讓研究、改稿與退回在實測中分別留下紀錄，並不表示 Paperclip 要有四人才能使用。

排錯時先辨認是哪一層失敗

同樣叫「agent 沒做事」，原因可能完全不同。Runs 裡若有 model_not_found，先檢查模型名稱與帳號可用性；若執行成功但內容沒有回答工單要求，就檢查任務描述與 agent 職責；若內容已留在留言、狀態仍未更新，就查執行環境能否回寫 Paperclip。不要把三種問題都用「再跑一次」處理，重試可能只會留下更多難辨認的版本。

這次案例正好遇到第一與第三種：移除不可用的指定模型後才成功產稿，而狀態仍需人工調整。對新手來說，最有用的排錯紀錄是「哪次 Run 對應哪張工單、出錯前改了哪項設定、最後看到什麼輸出」。有了這三項，下次才知道要修模型、修工單，還是修狀態同步。

新手該先雇幾個？

建議先一名 agent、一張小工單。讓它輸出能核對的短成果，確認登入、任務指派和成本紀錄都正常，再加研究與校對角色。我們這次一開始指定錯誤模型，導致數次失敗與重試；如果同時雇很多 agent，排錯會更難。

每個 agent 也要有自己的月預算。本站把內容企劃設為 USD 5，其他角色使用更低的教學測試額度；這不是實際花費。若用 ChatGPT 訂閱登入，Paperclip 的已記錄支出與你付的訂閱費可能分開顯示，詳見預算篇。
