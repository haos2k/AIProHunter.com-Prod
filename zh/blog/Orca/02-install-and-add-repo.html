Orca 安裝到第一個 Repo：先讓示範網站在本機跑起來

2026 年 11 月 21 日·8 min read

第一次開 Orca，我最不想遇到的畫面，是 agent 做完一大段修改後才發現：它工作的那份目錄根本沒有依賴，瀏覽器開的還是舊站。先拿青木咖啡這個可丟棄的示範 repo 試手。能打開網站、看到故意留下的四個紅燈，才算真正站在可工作的起點。

安裝檔與平台條件請以Orca 官方安裝頁當日內容為準。本站實作使用本機 Orca 1.4.256；版本可能與你看到的畫面不同，因此本文講可驗證的步驟，不把特定按鈕位置當成永遠不變的規格。Orca 桌面程式啟動後，先加入一個你可丟棄的 Git repo，再開第一個工作區；官方 First session也從這條路徑開始。

準備一份真的能重現問題的網站

本站把虛構「青木咖啡」示範站放在原始碼的 examples/orca-coffee-site/。它是單頁 HTML、CSS 與少量 JavaScript，不需要真實店家帳號。起始版本刻意有三個問題：390px 手機畫面中導覽蓋住預約按鈕、首頁仍寫過期的 2025 年活動、表單失敗時仍顯示成功。你可以先看最終版，再從紀錄中的起始 commit 重做；教學 repo、店名與表單測試資料都不是客戶資訊。

下載站點原始碼後，在專案根目錄安裝依賴並執行示範站測試。測試使用 Playwright；第一次執行若缺瀏覽器，要先按專案的 Playwright 安裝步驟補齊。起始 commit 的四項檢查應失敗，最終版四項應通過。若測試在兩個版本都通過，可能拿錯起點；若連測試腳本都不能啟動，先解決依賴，別急著建立三個工作區。

我會在筆記最上方寫四件事：repo 絕對路徑、目前分支、起點 commit、測試命令。後面拍的圖、看的 diff、跑出的紅綠燈，全部靠這四件事對版本。示範站可以用本機 HTTP 服務或直接開 HTML 預覽；表單只有前端模擬，測試時請用虛構資料。

在本站專案根目錄，重做最終版檢查的命令是：

pnpm install
node examples/orca-coffee-site/test.mjs

測試腳本會開 Chromium，在 390px 寬度檢查按鈕是否被蓋住、舊活動是否消失，以及表單成功與失敗訊息。本站起始 commit c764164 的四項全失敗，三項修正接回後四項全通過。若你從最終版執行卻看到失敗，先核對目前 commit 和 Playwright 瀏覽器是否安裝；不要直接把測試改成通過。這個小測試是後續每篇的共同驗收依據。

把 Repo 加入 Orca

在 Orca 選加入本機 repo，指向包含 .git 的專案根目錄，而非只指向 examples/orca-coffee-site/ 子資料夾。後者只是網站範例，不是獨立 Git repo。加入後確認 Orca 顯示的基準分支與你預期一致，再建立一個名為 coffee-check 的測試工作區。起點若選錯，之後看 diff 會混入不屬於本任務的變更。

建立後先不要開 agent，做兩項低成本檢查。第一，在新工作區看 Git 狀態，確認沒有上個任務留下的修改；第二，在新目錄啟動示範站或跑同一個測試命令。若它不能執行，記下錯誤究竟是「找不到套件」、「找不到環境變數」還是「程式測試失敗」。前兩者是工作區準備，第三者才是案例要修的行為。這樣你不會把安裝問題算進 agent 的返工。

如果第一次要用 CLI 建工作區，先執行目前版本的 Orca help 查旗標，並確認它連的是你正在看的桌面 runtime。CLI 在不同平台可能有不同名稱；不要照網路上的舊指令盲打。本文使用桌面介面做概念教學，後面的 CLI 篇才處理可重複命令。對入門者而言，先能看懂「我現在在哪個 repo／工作區」比背十個旗標重要。

Worktrees 文件說明新工作區有自己的磁碟位置。這意味被 Git 忽略的檔案，如依賴、快取和環境變數，不會自動都在新目錄。專案若要在新工作區啟動，先決定哪些檔案需重新安裝、哪些可共用、哪些必須各自保管。把私密憑證直接複製到公開範例不是解法。青木示範站不用帳密，因此很適合先練工作區，而不需要處理權限風險。

第一輪環境驗收卡

檢查 通過證據 失敗時先查
Orca 可啟動 能看到已加入的 repo 安裝與系統條件
Git 起點一致 分支與 commit 符合紀錄 是否選錯 repo 或起點
示範站可開 首頁與表單都能顯示 服務目錄、埠、瀏覽器網址
測試可執行 有明確通過或失敗輸出 Node、依賴與 Playwright
工作區可清理 知道修改是否要保留 未提交檔案與分支狀態

表格裡最值得留意的是「測試可執行」。它不要求起始版通過；本站故意讓四項檢查失敗。只要能清楚跑出失敗原因，環境就已經幫你把問題擺在桌上。若連測試腳本都開不起來，再回頭查 Node、依賴和 Playwright。

還要練一次「丟棄」。在 coffee-check 改一段無關緊要的文字，確認主工作區沒有跟著變，接著看 diff；如果只是練習，清除這個工作區，確認修改沒有被誤當成正式交付。若它是要保留的成果，先提交或移回正確分支，再清理。這一步可避免你日後把唯一的修正留在要刪除的目錄裡。

到這裡，你手上應該有一份能開啟、能跑測試，也知道如何丟棄的工作區。起始版四個紅燈是教材的一部分；等三項修正接回，才會變成四個綠燈。下一篇把它們拆進三個目錄，你會直接看到 worktree 的差異。
