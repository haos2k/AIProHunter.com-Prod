Orca Annotate AI Diff 怎麼審？用表單錯誤練習逐行退件

2026 年 11 月 26 日·8 min read

表單顯示「已送出」，你把請求切成失敗，它還是顯示「已送出」。這時候在聊天裡說「怪怪的」幾乎等於請 agent 再猜一次。比較有效的做法，是指著把狀態設成 success 的那一行，寫下失敗回應怎麼重現、改完要看到什麼。

Orca 的Annotate AI Diff 文件描述了在 diff 行上留言、一次送出多條意見，以及修改後追蹤註記的流程。以下表單案例是教學設計；本站這次沒有在 Orca 內完成這組註記與 agent 修正，因此不展示假截圖或假回覆。

先重現錯誤，再在 diff 上留言

青木咖啡的任務 C 是「表單送出要有清楚回饋」。驗收不能只看正常網路。先在本機示範站重現三態：資料不完整時不送出；後端確認收到時顯示成功；請求失敗時顯示錯誤與重試。若沒有可測的後端，就用測試替身檢查前端狀態，並在交付包標記「真實送達未驗證」。

打開 C 工作區的 diff，先檢查修改是否都在表單範圍。假如某一行在呼叫請求之前就把狀態改成 success，你的註記要貼在那一行，寫出條件與期待：「模擬 500 回應時仍顯示成功。請把成功訊息綁到後端確認結果；失敗時保留輸入、顯示重試；補成功與失敗測試。」這句包含重現方式、應有行為、修改邊界與驗收證據。

若同一輪還發現錯誤訊息對鍵盤使用者不可讀、送出按鈕沒有等待狀態，就在各自對應行留下意見。官方工具會把多個註記彙整成一批送給所選 agent；這比逐條聊天傳「還有一個」更容易保持同一輪的上下文。註記不能代替人判斷需求，送出前仍要確認沒有互相矛盾的要求。

一份好的審查清單

檢查位置 要問的問題 退件時的證據
請求前 是否提前顯示成功？ 失敗回應的重現步驟
請求中 是否防止重複送出？ 連點後的實際請求數
成功後 提示是否只在確認收到時出現？ 回應狀態與畫面
失敗後 輸入是否保留、能否重試？ 失敗畫面與操作步驟
表單外 是否碰到未授權區域？ 不相關檔案的 diff

如果這張卡原本只處理送出回饋，就把退件集中在送出狀態。審查中發現防垃圾訊息做得不夠，可以另外記下來估價；硬塞進同一輪，agent 可能連表單結構一起改了，你反而得重新驗更多地方。

修完後怎麼複驗？

Agent 交回新 diff 時，回到原註記所在行，看它是否真的改掉了造成錯誤的邏輯。若只換了文案、請求失敗仍顯示成功，不能因為留言被標記「已處理」就放行。重跑前述三態測試，再看新改動是否帶入意外：例如等待狀態無法解除、按鈕永遠禁用、錯誤後輸入被清空。

可以把三條註記寫成一輪完整的審查：第一條貼在成功狀態的設定行，要求只在收到成功回應後顯示；第二條貼在錯誤處理區，要求保留使用者已填資料並提供重試；第三條貼在測試檔，要求覆蓋失敗回應。送出前先讀一遍，確認三條描述的是同一個預期行為，且沒有同時要求「失敗時清空表單」與「失敗時保留表單」這種衝突。批次送出不是把十幾條隨手想到的意見一次扔給 agent，而是讓同一輪修正有清楚的終點。

複驗記錄可以寫：「第一輪因失敗仍顯示成功退回；第二輪模擬成功、失敗與資料不完整均符合需求；尚未連到真實收件後端，因此外部送達狀態待確認。」如果第二輪仍未通過，留下具體錯誤與重現方式，再送一輪；不要把相同一句「請修好」反覆貼進聊天。若 agent 修正一個問題卻新增別的問題，記下新增問題在哪個 commit 出現，這樣能判斷是回退還是局部修補較省時間。

審查時別忘了商業資料

表單可能收姓名、電話或其他聯絡方式。審查畫面和錯誤紀錄不該把真實顧客資料貼進公開 issue 或截圖；使用虛構測試資料即可。若店家沒有說資料應送去哪裡，程式上的成功提示也不能代替營運確認。你可以把這件事記成「需要店主指定收件者與保存規則」，待答之前交付一個可預覽版本，不宣稱已可處理真實訂單。

對店主來說，「送出後看得懂結果」與「真的收到客人資料」是兩筆不同的工作。這份 diff 只修前端狀態；若要建收件後端、通知與保存規則，需要另確認資料流和責任。把差別寫在交付單，比一張成功畫面更可靠。

逐行註記最有價值的時候，是一份 diff 裡有幾個明確錯誤，而且每個都能在修改後重測。本站實際修過示範表單，但這輪 Orca 註記與 agent 退件仍是教學步驟；請用自己的工作區留下真實回覆與測試結果。上一篇談排程，下一篇回到實際截圖，看看兩個工作區為何會給你兩種相反的畫面。
