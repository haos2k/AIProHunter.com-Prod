Orca 是什麼？先判斷你的網站工作需不需要多個 AI 工作區

2026 年 11 月 20 日·10 min read

手機版的預約按鈕被選單蓋住，首頁還掛著去年的八折活動，表單明明送出失敗卻說「已送出」。如果這是你週五下午接到的小網站案，直覺可能是開三個分頁趕快修。但三件事分別碰樣式、文案和程式，越趕越容易把測試圖、修改版本與客戶待答的問題混在一起。這正是我想拿 Orca 試的場景。

Orca 官方概覽把它定位為能在各自 Git worktree 中運行 agent、終端機和瀏覽器的開發工作環境。它不是替你決定需求的模型，也不會自動證明網站可上線。你可以把它想成一張有多個獨立工作桌的工作台：每張桌子放一項任務，最後再由人挑選、審查和整合成果。

先看一個真的能拆開的小案

本系列用虛構的「青木咖啡」委託做練習。店家網站有三個問題：390px 手機畫面中導覽蓋住預約按鈕，首頁仍顯示 2025 年活動，表單請求失敗也顯示成功。這是教學資料，不是真實客戶。本地示範站保留了有問題的起始版本，並用三個 Orca worktree 各修一個檔案；起始測試四項失敗，接回三份修改後四項通過。實測範圍是工作區、Git 變更與示範站畫面，沒有啟動 AI agent 或取得客戶收入。

青木咖啡很適合拿來看工作區的價值：導覽落在樣式、活動落在頁面、表單落在程式，三份修改各有可驗收的結果。本站實際從起點 c764164 建三個 Orca worktree，分別提交，再接回主線；四項 Playwright 檢查從全失敗變成全通過。這是示範站上的本機結果，沒有真實委託、案款或 agent 實跑。

Orca 到底幫你管哪一段？

第一段是隔離。Worktrees 文件說明每個工作區有自己的分支、磁碟檔案和 agent 終端機；你在 A 的未提交修改不會直接出現在 B。第二段是觀察：工作區瀏覽器、diff 和終端機放在對應脈絡，較容易追回哪張畫面來自哪條分支。第三段是回饋與交付：Annotate AI Diff能把逐行審查意見送回 agent；提交與 PR 仍須依團隊方式處理。

Orca 能安排工作，但交付責任仍在你。客戶沒給新的活動日期，工具不能替店家發明折扣；預約按鈕能點也不代表收款或預約系統已接通；前端顯示成功也不等於後端保存了資料。這些界線要寫進任務卡和交付說明。

用不用 Orca，先回答四題

問題 若答案是「是」 若答案是「否」
同時有兩項以上可獨立驗收的修改嗎？ 可考慮分工作區 一個工作區較簡單
你需要比較不同 agent 或不同方案嗎？ 隔離版本較有用 別為平行而平行
有人能審查 diff 和整合後測試嗎？ 可建立交接流程 先補審查能力
建新環境的時間可接受嗎？ 試兩個小任務 先量啟動成本

若四題都答「否」，先用普通編輯器、Git 和單一 agent 做完這次小案。若前兩題答「是」，Orca 值得試，但只用一個低風險任務起步。本站的示範站就是這種試作：能看見修正前後差異，也能在錯誤時整包丟棄，不會碰客戶唯一版本。

普通分支與多工作區，差別在哪裡？

只用 Git 分支也能把修改分開，但如果手上只有一個工作目錄，切分支前常要先提交、暫存或處理尚未完成的修改。當 A 的手機導覽還在測，B 的文案也要改，你可能忘了目前檔案來自哪條分支。Git worktree 讓兩份目錄同時存在，A 的服務可留在 A，B 的 diff 可在 B 讀。Orca 再把終端機、瀏覽器與審查放到對應工作區裡。這是流程上的便利，不是 Git 被取代；最後仍由 Git 追蹤 commit 和合併。

如果你已經熟練使用多個 Git worktree 與自己的工具組合，Orca 不一定是必需。它的價值在於省掉自己維護「哪個終端機、哪個瀏覽器分頁、哪條分支」對照表的心力。是否值得，取決於你的案型與審查量。相反地，若團隊連分支和測試都沒建立習慣，先把最小 Git 流程做穩，再增加 agent 數量比較安全。

用一輪小試作找出自己的門檻

選兩項彼此少碰同一檔案、半天內可驗收的任務。開工前記下起點版本、預期結果、舊流程通常花的時間。第一次先只開一個 Orca 工作區，跑通任務、diff 和測試；第二次再試兩個工作區。每輪都把環境準備、等待 agent、審查、返工與合併後測試算進去。若兩輪工作範圍不同，就不要直接相減，先註明差異。

試作還要有失敗條件：工作區若一直缺依賴、預覽常連錯服務、審查者看不完產出的 diff，就減少並行數，或先改善任務卡。開了更多 agent 只會讓待審隊列增加。青木案例的三個檔案很適合教隔離，但真實網站可能有共用 CSS、資料庫與部署環境；一旦兩項修改共享這些資源，先畫依賴再開工。

賺錢、省錢、省時間要怎麼驗證？

接案時，我會把這三項寫成可報價的成果：手機按鈕可操作、過期活動清掉、表單提示分清成功與失敗。範圍一清楚，客戶要新增優惠或後端收件，就有一個能討論的新需求，而不是一句「順便」。

報價單可把每項成果的「包含」與「不包含」寫成一句話。例如修預約按鈕包含手機與桌面驗收，不包含更換預約服務；清理舊活動包含移除過期資訊，不包含替店家設計新促銷。客戶追加時，你有原範圍可對照，也能清楚說明為何需要新工時。省錢不只看模型帳單：少一次錯版交付、少一輪無範圍的免費修改，都可能減少直接成本，但要有自己的案件紀錄才能證明。

省時要比較同範圍的總交付時間，包含建工作區、等待、審查、合併後重測。省錢要把模型與環境費、人工返工算進去。若沒有舊流程基準與帳單，先記錄，不寫「省了 30%」。最適合的第一步是挑一個可以在半天內驗收的小任務，跑完一輪，再決定是否擴到平行工作。

我會先用兩項互不相依的小修改試它：記下建立工作區花多久、切錯版本幾次、整合後是否要返工。青木咖啡的測試證明三份變更能隔開並接回，還不能替你的案子回答「省多少錢」。下一篇先把示範 repo 跑起來，讓每個人從同一個起點看這些問題。
