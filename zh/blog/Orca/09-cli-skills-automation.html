Orca CLI 與自動化入門：先建一個停用的網站檢查排程

2026 年 11 月 28 日·8 min read

每個工作日上午都打開同一個 repo、翻一遍待審工作區，再把狀態貼進筆記，這件事很適合考慮自動化。但排程一旦開了，agent 額度也可能跟著每天流走。我先做了一個平日九點的草案，讀回設定、確認它停用，再把它刪掉；這一輪只驗證設定，不假裝已經得到一份好報告。

Orca CLI 概覽說明命令列可管理工作區與瀏覽器；Scheduled automations 文件建議先以 disabled 建立排程，檢查後再決定是否啟用。本站在 2026 年 11 月 26 日本機 Orca 1.4.256 實際建立一個平日 09:00、Asia/Taipei、停用狀態的示範排程，讀回設定後即移除；沒有讓它執行 agent，也沒有產生定期報告。

先分清楚三種東西

先把三個名詞放回各自的位置：CLI 是從終端機操作 Orca；Skill 給 agent 一份操作說明，官方 Skills 文件能對照目前 CLI 版本；MCP 則讓支援的 agent 連外部工具。裝了 Skill 不等於開了排程，接了 MCP 也不等於有權替客戶動資料。Bots 文件還有另一種入口，這篇的停用草案暫時用不到。

本系列不需要把所有 Orca 指令背下來。先用唯讀命令確認 Orca runtime 可連、目標 repo 正確，再決定要不要建立工作區或自動化。命令語法可能隨版本變動，操作前以當前 CLI 的 help 和 skill 說明為準；不要複製舊文章的旗標直接在客戶案上執行。

一個安全的定期檢查草案

青木咖啡示範案若要每個工作日上午整理「目前有哪些待審工作區」，提示可寫：「讀取示範站與未完成檢查，列出需要人決定的事項；不要修改檔案、不要聯絡任何人。」目標必須明確指向示範 repo，時區設為 Asia/Taipei，先停用。這種排程可作為未來接案的服務：每天給客戶或自己一份待辦摘要，但要先量每次執行的模型費和人工複核時間。

本站的實測操作是建立一個名為「Orca coffee demo review」的停用排程，讀回後確認 enabled 為 false、timezone 為 Asia/Taipei、模式為每次新工作區，最後將它移除。這證明建立與讀取設定可行，不證明排程執行或報告品質。如果你只想試設定，停在這一步即可，不會定時啟動 agent。

在本站使用的 Orca 版本，核心命令形式如下；先用你本機的 help 核對旗標，並把 repo 路徑改成自己的測試庫：

orca automations create --name "Orca coffee demo review" --trigger weekdays --time 09:00 --timezone Asia/Taipei --prompt "Read the demo and summarize open checks. Do not edit files or contact anyone." --provider codex --repo path:/你的/測試/repo --disabled --json

建立後從輸出取 automation id，再用 show 讀回設定；不要只相信建立命令中自己輸入的文字。本站讀回時確實看到 enabled 為 false、Asia/Taipei 與每次新工作區，隨後用 remove 清掉測試項目。若你留下停用項目當草案，取一個能辨認用途的名字，並定期檢查是否有人改動它；停用不等於已經完成一套可靠的排程。

檢查欄位 為何要看
目標 Repo 避免排程跑到另一個客戶的程式
提示內容 限制為檢查與摘要，避免意外改檔
Agent 與帳號 決定實際額度與費用歸屬
時區與頻率 避免半夜啟動或重複執行
啟用狀態 草案階段保持停用

這次我讀回的關鍵是 enabled: false、Asia/Taipei，以及每次新工作區。建立命令裡寫了停用，仍值得用 show 再看一遍；移除後也該查清單，確認草案真的不在了。這才是這輪測試能支持的結論。

何時才值得啟用？

先手動完成一次相同檢查，記下需要的資料與人工判斷。再檢查排程草案是否只讀應讀的 repo，報告收件人是誰，失敗時要怎麼通知；若需外部訊息或改碼，先得到相應授權。啟用後也要定期看執行紀錄與費用，不能只因「自動化」就當它省時。若每天要花十分鐘修正摘要，一週總成本可能高於自己檢查。

以接案服務來說，可交付的是「每天檢查哪些工作待人審、週末提供未完成摘要」，而不是承諾 AI 會自行修好客戶網站。報價時把設定、提示維護、人工覆核、異常處理與 agent 額度分開列。若只跑在自己工作流程裡，也要記每週省下的重複操作時間，扣掉設排程和看錯誤的時間。排程能在你不打開工作區時啟動任務，卻也能在你沒注意時消耗額度，因此每次執行的上限與通知方式要先想好。

若排程要修改程式，請先從停用草案升級成有審查與回退路徑的流程。至少要求它在獨立工作區工作、交回 diff 和測試、等待人確認後才合併。若只做摘要，提示裡寫清「不得改檔、不得聯絡客戶」即可，但仍要看它實際取了哪些資料。本文的實測沒有執行排程，所以不能用它證明任何修改權限已安全限制。

這次實作停在 enabled: false，讀回確認後便移除了草案。若你想把它變成每天替你省時間的服務，先連續記錄手動檢查花多久，再跑一次可審查的試作，才知道節省是否大於模型費與覆核時間。上一篇的瀏覽器驗收表可作為提示素材；下一篇把已完成的修改整理給客戶看。
