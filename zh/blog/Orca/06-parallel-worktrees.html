Orca 平行工作怎麼排？用依賴圖找出真正能省的等待時間

2026 年 11 月 25 日·8 min read

三個工作區同時亮著，進度看起來很熱鬧。可是你只有一雙眼睛審 diff；手機導覽剛改了共用 CSS，表單按鈕可能又被影響。真正決定交期的，不是 agent 幾個一起跑，而是最後那份修改何時通過審查、接回後又要測多久。

官方 Worktrees 文件說明每個工作區有自己的分支、檔案與終端機；這讓平行修改可行，但合併仍是另一個步驟。以下青木咖啡三項網站修改是教學演練，時間數字只用於示範算法，不是本站實測或 Orca 效能宣稱。

先畫依賴，再開工作區

手機導覽 A、過期文案 B、表單回饋 C，乍看可以同時做。實際讀過 repo 才知道，A 和 B 是否共享首頁元件，A 和 C 是否共用按鈕樣式。先寫出「誰一定要等誰」：若 A 改全站按鈕樣式，C 的表單按鈕需要等 A 合併後重測；若 B 只改獨立內容檔，就可以先完成並審查。

一張簡單的依賴表就夠：

任務 最早開始 主要風險 合併後重測
B：舊活動文案 立即 客戶尚未給新資訊 首頁文字與連結
A：手機導覽 立即 共用 CSS 影響桌面與表單 手機導覽、桌面導覽
C：表單回饋 A 的共用樣式界線確認後 表單按鈕可能受 A 影響 成功、失敗、驗證狀態

這是排程假設，不是說 C 必然得等 A 完成。如果查過檔案，A 和 C 完全不碰同一處，就可以並行；若改同一個檔案也不一定要串行，但衝突風險與整合成本要算進去。任務拆分的依據是變更邊界與驗收條件，不是 agent 數量。

用關鍵路徑算省時，別把三段時間直接相加

假設 A 需 40 分鐘、B 需 25 分鐘、C 需 30 分鐘，這些都是教學數字。若全部串行，理論工作時間是 95 分鐘。若 A、B 同時開始，C 等 A 後做，最早完成時間由 A+C 決定，是 70 分鐘；B 在第 25 分鐘完成，不會把總時間再減 25 分鐘。然後還要加上人工審查、合併與整合測試。只算 agent 執行時間，會高估節省。

真正在案子裡，我會記五個時間點：開工、agent 停下、審查結束、合併、整合測試結束。兩個工作區可以同時產出，但審查若都排在同一個人面前，交期仍然排隊。模型同時執行還可能增加費用，這些都該進算式。

一次合併只增加一個不確定性

B 若純文案且已有人確認可以移除舊活動，先合併 B、跑首頁檢查。再處理 A，確認手機與桌面導覽；最後接 C，重跑表單三態。每合併一份，都記下新起點與測試結果。這樣若最後表單按鈕失效，你能回頭查是哪一步帶進的，不必在三份未合併 diff 裡猜。

如果 A 改了共用 CSS、C 也改同一段樣式，不要硬套「先 B、再 A、再 C」；先讓其中一方更新起點或抽出共用修改，再重新檢查。Orca 的隔離負責讓改動可辨認，整合順序仍靠人判斷。也別忘了新工作區可能缺 Git 忽略的依賴與設定，啟動時間要列進排程。

排程表怎麼用在真實委託？

先把每張任務卡拆成「開工、初稿、人工審查、修正、整合測試」五段，而不是只估 agent 寫碼。A 的手機導覽可能初稿很快，但兩種寬度、點擊路徑和共用樣式都要查；B 的文案修改可能只需幾分鐘，卻卡在店主沒有新活動資料；C 的表單若缺後端測試環境，就不能保證真實送達。把「待客戶回答」畫成外部依賴，別把它算成 agent 的執行時間。

若照這個假設排一個工作日：上午先確認三張卡，A 導覽與 B 文案開工；下午先查 B 的文字來源，再看 A 的手機畫面；確認共用按鈕樣式後處理 C，最後留時間做整合測試。日期只是示範，重點是 B 可能很早完成，卻仍要等店主確認新活動。這段等待應在進度表裡露出來。

若要估最早交付日，先找從開始到最後驗收最長的那條路。以上面的教學數字，A 接 C 的路徑是 70 分鐘；但若 A 之後需 15 分鐘人工審查、C 之後需 20 分鐘整合測試，整包最早也要 105 分鐘，還沒算客戶回覆。把 B 的 25 分鐘加到這條路上是重複計算；把審查與回覆完全略掉則太樂觀。實際案件以自己的紀錄替換假設數字，並標出哪一步由人或客戶控制。

什麼時候開兩個就夠？

如果案子只有一個小元件、完成時間短於建第二個環境與審查時間，一個工作區比較簡單。若有兩項能獨立驗收、等待時間較長、你能在等待時審查另一項，並行才有機會帶來實際收益。做完後以同範圍的舊流程比較總交付時間，包含返工與工具費；沒有記錄就不要報「省 30%」。

對這個小案，先讓文案與導覽各走一條線，表單等共用樣式界線確認後再安排，通常比把三張卡同時丟出去更容易掌握。若你的 repo 證明 A、C 完全不碰同一處，就改排程；表格服務的是現場，不是要現場服從表格。三張任務卡在上一篇，下一篇看怎樣把具體退件意見送回 agent。
