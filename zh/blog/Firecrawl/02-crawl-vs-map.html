Firecrawl Map 與 Crawl 怎麼選？先盤點文件網址再決定抓取範圍

2026 年 11 月 25 日·Updated: 2026 年 11 月 26 日·8 min read

接手一個開源元件庫時，工程師常被要求「把安裝和遷移文件都整理好」。若還不知道有哪些頁，直接抓全站會先得到一堆無關內容。這篇的成果是一張 URL 盤點表與抓取上限：先用 Map 找候選頁，再用 Crawl 讀需要的內容。兩者的差別會直接影響 credit、後續人工篩選時間，以及是否漏掉真正的遷移指南。

Firecrawl Map 文件把 Map 定位為找站內網址；Crawl 文件則描述從起點追連結並擷取頁面內容。這不是「哪個比較強」的問題。若只要知道有沒有 /migration、/install、/api，先拿網址清單。當你已決定要讀哪些頁的正文，再抓內容。對有明確 URL 清單的工作，第六篇還會比較 Batch Scrape。

先把盤點題目寫小

假設這次只查一個元件庫的文件站。工件不叫「整站知識庫」，而是一張能交給維護者複核的表：url、頁面用途、是否要全文、理由、原頁檢查結果。安裝指南與遷移說明標為優先，版本封存、新聞與條款先排除。這一步可手做在試算表；有了判準才值得用 API 擴大。

官方 Map 請求可以設定 url 與 limit。以下是讀者練習，需要可用的 Firecrawl API key；本站沒有宣稱此請求成功返回網址清單。

本站在 2026 年 11 月 26 日先用免金鑰對官方文件 /features 做相同範圍的 Map 試驗，回的是 HTTP 401：This endpoint is not supported by the keyless free tier. 這是權限限制，不是空的站點地圖。不要把 401 說成「找不到頁」；也不要貼一張手工整理的 URL 表，宣稱是 Map 真正輸出。本站已保存狀態與時間供編輯核對。

有 key 後如何把 Map 接到 Crawl

先對 Map 回來的 URL 去重、看網域是否都屬於目標站，再用路徑與頁面標題挑最多 3–5 個候選。若清單缺遷移頁，查網站自身導覽或 sitemap；Map 結果並非網站資訊架構的保證。不要因 URL 名稱有 install 就認定內容正確，連到原頁看標題、版本與更新日期。

接著才在小範圍做 Crawl 練習。依官方 Crawl 參數限制 limit、深度與允許路徑，先檢查一輪結果，再增加頁數。Crawl 是任務型工作，應保存任務 ID、狀態、成功頁數與失敗 URL，不能只記「送出成功」。若目標站有大量版本路徑，先鎖目前維護版；若同一頁有語系副本，表中註記選用哪個語言。

步驟 你真正要問的問題 停止條件
Map 有哪些可能相關的 URL？ 清單可人工分類，或已達小上限
人工篩選 哪些是安裝／遷移的當前版？ 原頁標題與版本已核對
Crawl 選中範圍有哪些正文？ 有足夠內容回答任務，無需繼續擴站

少花錢的關鍵是先設停止條件

以目前官方計費說明，Map 以呼叫計費，Scrape／Crawl 擷取頁面則按頁面與選項計算；方案與單價可能變動。設想一個文件站有 200 個 URL，但你的交付只用 5 頁：先篩 URL 可以大幅縮小待抓範圍，卻仍要把人工篩選時間記入成本。若 Map 的清單已能回答「遷移頁在哪」，甚至不必 Crawl。

遇到 401，先檢查額度與 key 權限，別換成無限制的爬蟲硬跑。遇到 Crawl 頁數超出預期，停下來查路徑規則與重複頁。真正省下的是抓取、清理、審稿三段的總時間，而不是單看 API 回了多少網址。下一篇以博物館開放時間練習如何判定已抓到的資訊能不能引用。

用一張小表避免範圍失控

第一輪盤點可把 URL 分成「必讀」、「候選」與「排除」。必讀是目前版本的安裝與遷移頁；候選可能是 FAQ 或相容性說明；排除的是舊版存檔與與任務無關的新聞。每列記理由，例如「路徑有 v1，但本次只查 v2」。當客戶後來要求補查舊版，你可以調整規則，而不是重新想一次哪些頁被漏掉。

同一個網址也可能因語言、版本參數或尾端斜線重複出現。去重時不要只做字串相等，先確認重新導向後是否是同一頁，以及英文與中文版本的內容是否真的一致。若文件站用 JavaScript 換內容而 URL 不變，Map 的 URL 清單更不能代替內容檢查。抽查每類至少一頁，才能知道清單的分類是否可靠。

真正要擷取正文時，給每次 Crawl 一個明確問題，例如「列出遷移到當前版本必改的 API」。結果若包含無關頁，就先縮路徑或減深度；不要在一份龐大的 Markdown 裡用模型猜哪段屬於遷移。若結果缺一頁，查 Crawl 狀態與原站導覽，將缺頁列進交付的例外清單。這使「沒找到」與「未成功抓到」成為兩種不同狀態。

最後把表格交給同事複核：他應能看出為什麼抓五頁、哪些頁尚未讀、哪個 URL 由人工補上。能重現範圍選擇，才算省下下一次盤點的時間。若每次都重新爬一遍整站，即使 API 很快，清理與審稿仍會反覆消耗工時。

盤點表完成後可加一欄「待確認的版本」。文件站若同時放穩定版與預覽版，同一個安裝步驟可能互相矛盾。要交付給實際開發團隊，就把目標版本寫在表頭，並讓每個 URL 都能回到該版本；無法判定版本的頁面先不當作升級依據。
