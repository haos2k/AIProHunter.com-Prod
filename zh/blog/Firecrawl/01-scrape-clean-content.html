Firecrawl Scrape 實戰：把 SQLite 更新頁整理成可查核的 Markdown

2026 年 11 月 25 日·Updated: 2026 年 11 月 26 日·8 min read

獨立軟體作者每次發版，都要從上游更新說明挑出會影響自己產品的變動。複製網頁到筆記看似簡單，導覽列、頁尾與舊版本資訊常一起進來。這篇用 SQLite 3.54.1 官方版本頁做一次 Firecrawl Scrape：你會拿到 Markdown，並知道哪些地方仍須回原頁核對。這是整理資料的起點，不是讓模型直接替你宣告升級安全。

這次真的抓了什麼

本站於 2026 年 11 月 26 日向 Firecrawl v2 的 /scrape 送出該網址，要求 markdown 格式。免金鑰請求回 HTTP 200、success: true、來源頁狀態 200，Markdown 長度為 7,111 字元。版本標題與 2026-10-16 日期都出現在結果中。這些是本次觀測，不能保證日後頁面長度或免金鑰額度相同；請求摘要已保存在本站的系列實測紀錄，供編輯核對。

你可以先以最小請求重做，暫時不要加入 JSON schema 或其他選項。官方 Scrape 文件說明 formats 的用途；公開頁面可先試免金鑰入口，正式工作仍應核對當前額度與授權。

拿到回應後先看三件事：HTTP 是否成功、success 是否為 true、來源 metadata.statusCode 是否合理。再把 data.markdown 存進工作檔，不要把整份 API 回應當成發布稿。若回應有錯，保留網址、時間、狀態碼與訊息；重試前先查頁面是否仍公開，避免一個失敗請求變成無限迴圈。

Markdown 乾淨到什麼程度？

這次結果保留了更新頁的標題與條列內容，讓你可以搜尋版本號、把不同版本排在一起比較。不過，它也保留網站導覽文字與「Prior changes from version 3.54.0」段落。若你只要 3.54.1 的新增內容，直接整份交給摘要工具，模型可能把前一版的變動寫進本版。Scrape 把 HTML 變成較好處理的文字，並沒有替你定義文章邊界。

我會先做一張小核對表，才開始寫自己的更新通知：

欄位 Markdown 所見 回原頁要確認
版本 3.54.1 URL 與頁面標題是否相符
發布日期 2026-10-16 日期是否屬於本版
變動段落 條列及舊版延伸 從哪個標題開始算前版內容
連結 文字及目標網址 重要下載或文件連結能否開啟

這個表才是可交付的工件。客戶問某個變動來自哪裡，你能指回官方版本頁與段落，而不是只交一段沒有來源的 AI 摘要。若要貼進產品公告，再由維護者判斷哪個變動真的影響目前使用的 SQLite 版本與編譯選項。

什麼時候值得用 Scrape？

單頁、公開、要重複整理或接後續程式時很合適。先固定網址、格式與核對欄位，第二次發版才容易比較。若只讀一頁且偶爾做一次，瀏覽器複製可能更快；不要為了「自動化」增加 API、儲存與審稿流程。若頁面是互動式內容、需登入或禁止存取，也不能用這次靜態版本頁的成功經驗推論一切可抓。

省時間的衡量方法很簡單：記下手工複製、刪掉雜訊、核對來源的分鐘數；再記下 Scrape 請求、修剪 Markdown 與查核所花時間。若第二次以後能重用核對表，才有可量的效益。Firecrawl 計費文件目前把一般 Scrape 視為按頁計費，額外抽取選項另算；大量抓取前先估數量。

下一篇會處理「我還不知道要抓哪些頁」；那是 Map 與 Crawl 的選擇，和這篇已知單一網址的任務不同。此篇可帶走的判斷是：拿到 Markdown 只完成格式轉換；版本、日期和內容邊界仍要對原頁驗證。

把第一次整理變成下次可重用的流程

第二次查更新頁時，先不要直接將新 Markdown 覆蓋舊檔。用「產品、版本、原始 URL、抓取日期」組成檔名，保留前次輸出，才能看出是上游真的改文案，還是抓取器這次少讀了一段。若網站將同一 URL 的內容改成新版，只有保留來源快照與時間，才能回答客戶「當初公告依據是什麼」。快照只供內部核對，公開引用仍以原站的授權與現行內容為準。

可以用一個小範圍的人工檢查取代「全文看起來合理」：先核對標題和日期，再抽查第一條與最後一條變更，最後找到「Prior changes」的分界。若最後一條出現在分界之後，就表示你切得太遠；若第一條沒在 Markdown 裡，表示擷取可能漏段。這三個點不保證全文完整，但比只看 success 多一層具體證據。

內容要交給模型摘要時，把已裁切的本版條列與原網址一起給，並要求每個摘要項目對到原文一條。模型若提出「效能提升百分比」而原文沒有量測，刪掉該句。對軟體作者來說，版本公告最有價值的是準確告訴讀者哪些變動影響他們，並非把整篇官方 release note 改寫一次。

若頁面含重要表格或程式碼，另外抽查標點、縮排與連結。Markdown 有時把視覺欄位攤平成文字，內容仍可讀卻失去欄位對應；這類資料不適合只靠文字比對。建立一份「已核對／待確認／不採用」標記，讓下一位編輯知道哪些結論能引用，哪些只是抓取到的線索。

若你的更新通知要服務非工程讀者，再做一次「影響範圍」檢查：每個條目是修正錯誤、增加功能，還是只改開發者介面？原文沒有說明的影響不要推測。這會讓文章比單純翻譯更新說明更有用，也減少因誤解版本差異造成的支援工單。
