spec、plan、implementation 有什麼差別？Superpowers 的正確落地流程

2026 年 3 月 29 日·7 min read

前面幾篇談過「先啟用習慣、先 brainstorming 拿到設計共識」。接下來很常卡在一個問題：設計同意了，然後呢？ 很多人這時候會直接說「那你開始寫吧」——結果代理一頭栽進改檔，改到一半才發現 根本沒有人把「要做幾步、每步驗證什麼」寫清楚。這篇標題裡的 spec、plan、implementation，用白話對齊成下面三個層次，並說明 Superpowers 裡 writing-plans 在整條鏈上站哪一站。

**在這個系列的語境裡，spec（規格）你可以先這樣記：**把已經聊過、對齊過的 需求與設計，整理成一份 雙方（你與代理）都確認過 的說明文——寫清楚要做什麼、刻意不做什麼、怎樣算完成、有什麼限制或介面約定；還不是「第幾步改哪個檔」那種執行表。plan（計畫） 才是那份 可照著做的步驟與驗證點（誰先做什麼、順序、每段怎麼檢查）。implementation（實作） 則是依計畫真的去改程式、跑測試、交成果。新手答題用一句話就夠：spec 定「做什麼與邊界」；plan 定「用什麼順序做」；implementation 才是「真的在做」。

需求、設計、計畫、實作的差別

上面三個詞，是 成果型態 的分法；若把前半段再細拆成「想法怎麼長大」，從模糊到具體常常是這條線：

  1. 需求（Requirement）：「我們要解決什麼問題？誰會用到？怎樣算成功？」——還在講 為什麼做、做給誰，細節可以還很粗。
  2. 設計（Design）：「用哪種做法、邊界在哪、不先做什麼、和現有程式怎麼接？」——已經在講 選哪條路、取捨是什麼，通常 brainstorming 會幫你把這段對齊。
  3. 計畫（Plan）：「拆成哪幾步、先後順序、每步做完要檢查什麼、風險點在哪？」——這是 可執行的路線圖，還沒寫程式，但已經知道「下一步不是亂猜」。
  4. 實作（Implementation）：真的改檔、跑測試、開 PR——照著 spec 的範圍與完成定義、再依 plan 的順序 把東西做出來。

把 1、2 對齊並寫成被確認的文件，就是前面的 spec； 接著才進入 3 的 plan，最後才是 4。很多人把「設計講完了」當成「可以開工了」，其實中間可能還缺 落成 spec（不然共識只留在對話裡），也還缺 plan 這一層。缺了它們，實作階段就容易變成 邊寫邊發明範圍與流程，返工機率直接拉滿。

writing-plans 的角色

在 Superpowers 的語彙裡，writing-plans 這類流程 skill 扮演的角色很單純：在你已經有方向（甚至已有粗 spec）之後，把「怎麼落地」寫成一份別人（含未來的你）跟著做就不會歪掉的計畫。

它不是在重複 brainstorming：brainstorming 偏 選方案、對齊意圖；writing-plans 偏 把選定的路拆成步驟、標檢查點、預留回頭路。你可以把它想成：專案經理在寫 sprint 任務清單，只是讀者常常是 AI 代理——所以計畫要寫得夠明確，代理才不會自己腦補捷徑。

實務上它常涵蓋：要動哪些檔案或模組、建議順序、每段完成後如何驗證、哪裡可能踩雷要先試。重點不是寫得漂亮，是 可執行、可檢查。

正確的落地順序

新手可以記這個順序，和前面幾篇是接起來的：

  1. using-superpowers：確認這次該走哪些流程、別一進場就寫碼。
  2. brainstorming（需要時）：把需求講清楚、方案列出來、選定一條路與邊界——設計共識。
  3. writing-plans（有規模或有多步時）：把落地路徑寫成計畫——誰先做什麼、怎麼驗證。
  4. implementation 類 skill / 實作：照計畫改程式；若後面還有 TDD、除錯、完成前驗證 等品質把關，再依情境接上（下一篇會專門談）。

不是每個改一行的小修都要寫長篇計畫，但只要你心裡出現「這大概要好幾步」或「我怕改 A 壞 B」，先寫短計畫通常比事後救火便宜。

為什麼沒有 plan 就開工很危險

沒有 plan 的實作，常見劇本如下（聽過就算賺到，最好別親身體驗）：

  • 代理先改最容易下手的檔案，後來才發現順序錯了，要整段回滾。
  • 做到一半才發現缺依賴、缺測試、缺環境，計畫變成「邊做邊發明」。
  • 你以為完成了，其實只完成畫面或只完成一半 API，因為從來沒寫「完成定義」。
  • 多人或多次對話接力時，下一個接手的人看不懂「當初為什麼這樣改」，只能再通靈一次。

Plan 的存在，就是把 「我以為你懂」 變成 「白紙黑字寫在這」。對人對AI Agent都一樣：少通靈、少返工。
