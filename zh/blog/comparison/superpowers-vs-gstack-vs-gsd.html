Superpowers、Gstack、GSD：三大 AI Agent 開發利器完整比較

2026 年 4 月 19 日·14 min read

你應該看過這三個名字至少出現過一次：Superpowers、Gstack、GSD（Get Shit Done）。

都是「讓 AI 開發更有效率」的工具，都在 Claude Code 生態圈裡流傳——但如果你問「我該用哪一個」，你得先知道它們解的是三個截然不同的問題。搞錯問題，選對工具也沒用。

這篇的任務：把這三個工具的核心定位說清楚，讓你一次看懂它們的差別、各自的適用場景、以及什麼時候要疊在一起用。

先說結論：三個工具，三個層次的問題

工具 核心問題 解法 主要對象
GSD 你有 AI 工具，但任務還是做不完 修執行斷點與完成心法 你自己（人的執行層）
Superpowers AI Agent 一開工就亂衝，結果不穩定 強制走流程，skill 管控代理行為 代理的流程層
Gstack 代理在每個階段的思考品質不夠專業 角色切換，給 AI 正確的認知模式 代理的品質層

這三層不重疊，但可以疊加——後面我們會說怎麼搭配。

GSD：先修你自己

核心問題：你用了 AI 為什麼還是做不完事？

GSD（Get Shit Done）不是一個代理框架，不是 skill 套件，也不是 slash command 的集合。它是一套診斷你自己執行斷點的思維框架。

GSD 認為，大多數人用了一堆 AI 工具之後，生產力沒有大幅提升，問題出在三個非常具體的地方：

  1. 模糊任務症候群：待辦清單裡有的是意圖，沒有動作。「做 X 這件事」不是任務，「打開這個檔案、改第三段、加上這兩個資料點、存檔」才是。AI 幫你生了更多內容，但那些內容只是在意圖層停著。

  2. 啟動成本過高：每次用 AI 對話都是全新上下文，你得重新交代背景。AI 讓這個問題更嚴重，不是更輕鬆——你寧願開新對話聊個容易的問題，也不願面對那件需要重建上下文的任務。

  3. 收尾恐懼：「再改一下」這句話殺死了很多本來可以完成的東西。諷刺的是，AI 讓「再改一版」的成本變超低——以前改一版要半小時，現在三分鐘——所以你可以無限循環修稿，但永遠沒有收斂。

GSD 的解法是在任何工具技巧進場之前，先建立一個信念：Done > Perfect。一個不完美的完成品，比永遠沒完成的完美計畫有用。

GSD 適合誰

  • 有很多 AI 工具但任務還是塞滿的人
  • 計畫做了很多但完成率低的人
  • 「感覺很忙但沒什麼真的做完」的人

GSD 不擅長什麼

  • 它不管代理怎麼跑、品質好不好
  • 它不提供具體的技術工作流
  • 它是思維框架，需要你自己判斷和執行

Superpowers：讓代理不亂衝

核心問題：AI Agent 太急著動手，流程不穩定。

Superpowers 是一套給 AI 代理用的「開發工作流」，由一疊叫做 Skills（技能說明檔）的 Markdown 文件組成，加上一條鐵律：有對應的 skill 就先用，有流程就先走。

它解的問題非常具體：沒有流程的代理，你叫它做一件事，它會直接開始改十個檔。有時候看起來衝很快，但返工比例極高。結果往往是你花了很多時間，代理也花了很多 token，最終得到一個脆弱的結果。

Superpowers 把開發拆成幾個固定階段：

  1. 先探索需求（using-superpowers → brainstorming）——釐清「要做什麼」，而不是直接下手
  2. 再寫計畫（writing-plans）——大功能先有路線圖
  3. 然後實作（可搭配 test-driven-development）——先定義怎麼算對，再寫到對
  4. 最後驗證（verification-before-completion）——說做完之前要有證據，不是感覺

這些 skill 背後的邏輯是：把正確的開發習慣，從「靠記憶力執行」變成「看到這個 skill 就照這套劇本演」。代理不會忘記、不會跳過——只要流程 skill 在，它就按流程走。

Superpowers 的鐵律有幾條值得記：

  • 「這次很簡單」是跳過流程最常見的藉口，也是最常造成問題的那種。
  • 「講得超細」不等於雙方對焦完成。 流程 skill 的很大一部分功能，是在逼這件事發生。
  • 「Superpowers 讓代理變慢」是錯覺。 對話步數可能多一點，但整體工時通常反而少，因為少了很多「以為做完其實沒做完」的來回。

Superpowers 適合誰

  • 已經在用 Claude Code 或類似工具的開發者
  • 代理跑起來「感覺很拼命但結果不穩定」的人
  • 想要可重複、可預期的開發節奏的人

Superpowers 不擅長什麼

  • 它不管代理「用哪種思維模式」在想問題——只管流程順序
  • 它不提供 code review 或 QA 等品質保證機制
  • 對完全不熟悉 AI 代理的新手，學習曲線可能稍高

Gstack：給 AI 正確的認知模式

核心問題：代理在每個階段用的是「通用助手」腦袋，品質稀釋。

Gstack 是 Garry Tan（Y Combinator 總裁）開發的 Claude Code skill 套件。它的核心洞察是：

你不能用一個「通用助手」的模式，同時完成 CEO 思維的產品決策、偏執型工程師的 code review、以及 QA 的功能測試——這些角色的認知模式互相衝突，混在一起只能得到稀釋版。

Gstack 的解法是提供 9 個 slash command，每個對應一種認知模式：

Slash Command 角色 核心問題
/plan-ceo-review Founder / CEO 這個功能值得做嗎？有沒有更好的解法？
/plan-eng-review Engineering Manager 架構、邊界、edge case、test coverage
/review 偏執型資深工程師 能過 CI 但會在 production 爆的問題
/ship Release Engineer Sync、test、push、PR 一條龍
/browse QA Engineer（有眼睛版） 用真實瀏覽器點你的 app
/qa QA Lead + 修 bug 找問題、修問題、輸出健康分數
/qa-only QA Reporter 只報告，不動你的程式碼
/setup-browser-cookies Session Manager 匯入真實 cookies 給 headless session
/retro Engineering Manager（回顧版） 分析 commit 歷史、出貨速度

Gstack 的典型工作流是：先用 /plan-ceo-review 確認值不值得做 → 再用 /plan-eng-review 設計架構 → 實作 → /review 找 production 級問題 → /qa 瀏覽器實測 → /ship 一鍵交付。

差別不是 AI 的聰明程度，而是被問的問題不同。/review 會系統性查 race condition、N+1 query、trust boundary violation——不是因為模型更強，而是它的認知模式讓它問的是那些問題。

Gstack 適合誰

  • 已經在用 Claude Code 寫生產程式碼的開發者
  • 想要更穩定品質保證的獨立開發者或小團隊
  • 做到某個規模後，開始擔心「有沒有漏掉什麼」的人

Gstack 不擅長什麼

  • 它全開的時候 token 消耗很高，每個角色都有自己的 context
  • 它不管「要不要做這件事」之前的執行心態問題（那是 GSD 的地盤）
  • 它不強制流程順序，需要你自己判斷什麼時候叫哪個 skill

三個工具的直接對比

維度 GSD Superpowers Gstack
解決的問題 人的執行斷點 代理的流程紀律 代理的認知品質
主要使用者 所有 AI 工具使用者 Claude Code 用戶 Claude Code 進階用戶
介入時機 開始任何工作前 代理開工時 開發各階段切換
學習成本 低（思維框架） 中（安裝 + 習慣建立） 中（9 個 command 的場景判斷）
Token 消耗 無 中 高（每個角色有獨立 context）
最大優勢 讓你真的做完事 讓代理有規律、少返工 讓代理在對的時候問對的問題

三個工具可以一起用嗎？

可以，而且它們互補得很好——因為每個工具管的是不同層次。

這是一個典型的搭配使用場景：

場景：你要做一個新功能

  1. GSD（你的執行層）：先用 GSD 心法確認「做完的邊界是什麼」、「完成條件是什麼」。讓這次任務不是一個模糊意圖，而是一個有明確 DoD（Definition of Done）的工作。

  2. Superpowers（代理的流程層）：開始跟 Claude Code 對話時，先走 using-superpowers → 需求不清就 brainstorming → 大功能就 writing-plans → 說完成前跑 verification-before-completion。代理不會亂衝，流程有保證。

  3. Gstack（代理的品質層）：在對的時間叫對的 skill——想確認值不值得做先跑 /plan-ceo-review，架構設計完成後跑 /plan-eng-review，實作完跑 /review，準備出貨前跑 /qa + /ship。每個階段問對的問題。

簡化版口訣：

GSD 管你是否真的準備好動了 → Superpowers 管代理走的路對不對 → Gstack 管代理每一步做得夠不夠好

我應該先用哪一個？

如果你剛開始用 AI 做開發：先 GSD。
不管代理再強，如果你的任務邊界不清、完成條件模糊，代理幫你生出來的東西也只是更快的迷路。先把自己的執行紀律打好，再談代理管控。

如果你已經有 AI 工作流、但結果不穩定：Superpowers。
代理跑起來很拼命但返工多、或每次結果難預期？很可能是流程問題，不是模型問題。Superpowers 的 skill 套件讓代理行為可預期。

如果你已經在用 Claude Code 寫生產程式碼：Gstack。
流程有了，但你開始擔心「有沒有漏掉什麼能過 CI 但在 production 爆的問題」、「這個功能值不值得做」——Gstack 的角色模式就是在這個層次補洞。

如果你想要最完整的體驗：三個一起用。
GSD 管你，Superpowers 管流程，Gstack 管品質——三層都到位，獨立開發者一個人可以跑出接近完整開發團隊的節奏。

最後一句話

這三個工具被比較的原因，是它們都出現在「讓 AI 開發更有效率」這個標籤下——但它們針對的其實是三個完全不同的失敗模式：

  • 你自己動不了：GSD
  • 代理跑錯了方向：Superpowers
  • 代理做得不夠好：Gstack

搞清楚你現在卡在哪一層，才知道哪個工具最值得先用。
