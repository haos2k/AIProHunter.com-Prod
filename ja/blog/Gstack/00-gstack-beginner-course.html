Gstack 入門コース：Claude Code をバーチャル開発チームに変える

2026年4月19日·8 min read

Claude Code でコードを書き始めて 2 週間も経つと、ある問題に気づくはずです：AI は言うことを聞いてくれるが、「本当にそれでいいですか？」とは聞いてくれない。

機能を追加してと言えば追加する。このロジックをリファクタリングしてと言えばリファクタリングする。この endpoint を直してと言えば直す——そして 2 つの新しいバグを生み出し、さらに 3 往復の会話でその後始末をすることになる。

問題は Claude が賢くないわけではありません。問題は、すべての作業を同じ頭脳でやらせ続けていることです：プロダクト判断、アーキテクチャ設計、コードレビュー、テスト、デプロイ——すべてが 1 つのコンテキストに混在し、1 つの会話で完結しようとしている。

Gstack が解決しようとしているのは、まさにこれです。

このシリーズが解決する問題

Gstack（正式名称 GStack）は Y Combinator CEO の Garry Tan がオープンソースで公開した Claude Code skills フレームワークです。核心的なコンセプトはたった 1 文です：

「Planning is not review. Review is not shipping. Founder taste is not engineering rigor. If you blur all of that together, you get a mediocre blend of all four.」

平たく言うと：AI に適切なタイミングで適切な頭脳を使わせる、一つのモードで押し通させない。

Gstack は 9 つの skill を提供し、それぞれがソフトウェア開発サイクルの異なる役割に対応しています：CEO 思考のプロダクト意思決定、エンジニア視点のアーキテクチャ設計、偏執的なシニアエンジニアのコードレビュー、自動化 QA テスト、ワンクリックデプロイ——各 slash command の背後には、切り替えられた認知モードがあります。

このシリーズでは、このフレームワークをインストールから実際のシナリオまで、6 記事でわかりやすく解説します。

このシリーズが向いている人

  • すでに Claude Code でコードを書いているが、出力品質が不安定でよく手直しが必要な人
  • レビュー、テスト、デプロイの各段階で手動作業を減らしたいエンジニア
  • 一人でプロダクトを作っており、AI を「タイピングツール」から「バーチャル開発チーム」にアップグレードしたい独立開発者
  • Garry Tan が週 10,000 行のコードを書くという数字を見て、どうやっているのか気になった人

Claude Code をまだ使ったことがない方には、このシリーズは少し速すぎるかもしれません——まず Claude Code 自体に慣れてから戻ってくることをお勧めします。

シリーズ読書ガイド

この 6 記事は「なぜ Gstack が必要か」から始まり、インストール、各コア skill の詳細解説を経て、実際の開発シナリオでの統合デモで締めくくります：

1. AI アシスタントに「ロール切り替え」が必要な理由：Gstack のコアロジック まずメンタルモデルを構築します——Gstack が解決するのは「AI が賢くない」問題ではなく、「AI に正しい認知モードを与えていない」問題です。この記事を読み終えると、なぜ 9 つの skill が 1 つの万能プロンプトより効果的なのかがわかります。

2. Gstack インストールとクイックスタート：10 分で 9 つの skill をセットアップ GitHub clone からセットアップ完了まで、よくあるインストール問題の解決策付き。読み終えたら最初の slash command を実行できます。

3. Plan Review デュアルモード：CEO 思考 + エンジニアアーキテクチャ、なぜ分けて使うのか /plan-ceo-review と /plan-eng-review は Gstack で最も投資対効果の高い 2 つの skill です——一方は「やるべきか」を問い、もう一方は「どうやれば正しいか」を問います。この記事では両者の違いと使いどきを明確にします。

4. Code Review と Ship：偏執的レビューからワンクリック納品まで /review は CI を通過しても production でクラッシュするような問題を探します。/ship は sync、test、push、PR を 1 つのコマンドに圧縮します。この記事では内部ロジックと組み合わせ方を解説します。

5. QA と Browse：AI に目を与えて、アプリを本当に「見せる」 /qa は git diff を分析し、影響を受けたページを特定してテストし、バグを修正して再検証——0 から 100 のヘルススコアを出力します。/browse は AI に本物のブラウザでアプリをクリックさせます。この記事では設定に時間をかける価値がある理由を説明します。

6. 実際の開発シナリオ：新機能から production までの Gstack 完全ワークフロー 前の 5 記事のコンセプトをつなげ、実際のシナリオで全プロセスをデモします——/plan-ceo-review から始まり、/ship で終わるまで。

推奨読書順序

1 → 2 → 3 → 4 → 5 → 6、順番通りに読むのが最も安定です——コンセプトを理解してからインストール、インストールしてから各 skill を使い、最後に全フローを通して走らせます。

時間が限られている場合は：少なくとも 1（なぜ必要かを知る）と 2（ツールを実際にインストールする）を読んでください。他の記事はニーズに応じてスキップ読みしても構いませんが、3 は最も投資対効果が高いので飛ばさないことをお勧めします。

クイックスタート版

一言版：Gstack をインストール → 新機能は先に /plan-ceo-review + /plan-eng-review を実行 → 実装後に /review を実行 → 問題なければ /ship を実行。
